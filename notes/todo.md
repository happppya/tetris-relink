> **Observed multiplayer bugs found during the pass:**
> - **Placed piece vanishes** — ✅ FIXED. Root cause: the server compared a client's real board (with placements) to its garbage-only mirror (built only from clear events, never placements) and force-sent a `resync` that overwrote the stack, erasing pieces ~0.5s after every lock. Fix: `lock` now carries the placed **`cells`**, and the server **reconstructs a true authoritative board** from them (`server/authority.ts`), so a corrective `resync` only ever fires on real divergence — it can no longer erase a healthy stack. The client applies a legitimate `resync` to heal genuine desyncs. Covered by `server/session.test.ts`, `server/message-loss.test.ts`, `server/multiclient.test.ts`, `server/authority.test.ts`.
> - **Leave ≠ die** — ✅ FIXED. Leavers are permanently removed (`Match.removePlayer`) instead of forfeited-per-round, so a 1v1 survivor wins the match instead of playing a ghost forever. Covered by `src/engine/match.test.ts` + `server/disconnect.test.ts`.
> - **Opponent boards invisible** — ✅ FIXED. The server relays 20-row visible boards (`board_update`), but the render path demanded 24-row boards (`renderBoard` + the component's `hasBoard` check), so opponents' boards never drew. Fix: `renderBoard` pads a 20-row visible board with hidden rows so both shapes render, and the opponent check accepts 20 rows. Covered by `src/render/canvas.test.ts`.
> - **Hold piece invisible** — ✅ FIXED. The multiplayer game screen never rendered hold. Fix: added a HOLD canvas (same pattern as VersusScreen) driven by `game.hold`; `game_start` also resets hold/combo/streak so nothing carries between rounds.
> - **Leave button breaks server comms** — ✅ FIXED. The mid-match LEAVE button only cleared local state and never told the server, leaving the player in the match and blocking new lobbies (`already_in_lobby`); the server's `leave_lobby` handler also never removed players from the session. Fix: the button sends `leave_lobby`, and the server routes both `leave_lobby` and socket disconnect through a shared `removeFromMatch` (removes from session, broadcasts `player_left`, resolves 1v1 matches). Covered by `server/disconnect.test.ts`.
> - **Perpetual rollback of placed pieces** — ✅ FIXED. Finished matches stayed in the server's session map and `sessionFor` didn't filter by status, so a second match in the same lobby routed locks to the finished match's authority while snapshots went to the active one — every placement then "rolled back" via resync. Fix: `sessionFor` only returns active matches, and sessions are deleted on `match_won` and lobby teardown. Covered by `server/sequential-matches.test.ts`.
> - **Flaky `server/message-loss.test.ts`** — ✅ FIXED. `LossyProxy` silently dropped the first client message (`create_lobby`) when its upstream socket wasn't open yet under load; it now buffers client messages until the upstream link opens.
> - **Opponent boards carry over into a new round** — ✅ FIXED. A `board_update` from the previous round could arrive after the next round's `game_start` and repopulate the opponent list with a stale board. Fix: `board_update` is tagged with the round (`shared/protocol.ts` + `server/index.ts`) and the client (`MatchClient`) drops relays whose round ≠ the current round; `game_start` also resets opponents/hold/combo/streak.
> - **E2E through the real client stack** — ✅ ADDED. `src/net/match-client.ts` extracts the game screen's netcode into a shared `MatchClient` (used by both the component and tests); `src/state/lobby.ts` became a `createLobbyStore(conn)` factory (the `useLobby` singleton is unchanged). `src/net/multiplayer.e2e.test.ts` drives two real clients (`NetConnection` + store + `MatchClient` + engine `Game`) against the real server over real WebSockets: full round with hold + opponent boards + garbage routing, guest leave mid-match, host leave mid-match (host transfer), and two consecutive matches in one lobby with zero resyncs.
> - **Server load & performance** — ✅ ADDED/MEASURED. `server/load.test.ts` pushes the real server with 48 concurrent clients across 6 matches (relay + ping latency), lock→garbage routing latency, 5 rapid consecutive matches (session-map growth), and leave/disconnect churn (full state reclamation). Measured: snapshot→ack p95 14–16ms, ping p95 4ms, lock→garbage p95 1ms at 48 clients; sessions/lobbies/conns fully reclaimed after churn; finished sessions never accumulate. Found + fixed one real issue: **message amplification** — the server echoed every `board_update` back to the sender who had just sent it (576 of 576 snapshots self-echoed = 1/N of relay traffic wasted). Fix: `sendToLobbyExcept` skips the sender for `board_update` (self-echoes now 0). `target_update` deliberately still reaches the sender (clients need auto-reassigned targets). `ServerHandle` gained a `stats()` accessor for leak measurement.
> - **Leave/disconnect boundary races** — ✅ STRESSED + FIXED. `src/net/multiplayer.e2e.test.ts` gained 8 race tests through the real stack (NetConnection + store + MatchClient + Game vs the real server): both players leaving at once, duplicate leave presses, locks/snapshots landing after the opponent leaves, a disconnect landing exactly at match_end, both players disconnecting mid-match, send-leave-then-close, a 3-player leave mid-match (match continues for the survivors), and a server-initiated connection drop (the dropped player's client must clear the stale match and reconnect to the lobby). Found + fixed: (1) server answered an in-flight `lock` with `not_in_match` after the session ended — now dropped silently like snapshot/topout/target; (2) the store's `leaveLobby` sent twice on a double-press → `not_in_lobby` error — now guarded; (3) `scheduleReconnect` reconnected to the default URL instead of the endpoint the store connected with — now remembers it; (4) `connection_lost` left `match` set so the app stayed stranded on the dead game screen — now clears the match ("disconnect = leave the match") and falls back to the lobby/menu. Added `ServerHandle.kick()` for drop simulation.
> - **Lobby list not live** — ✅ FIXED. The public lobby list only updated on explicit REFRESH: (1) the MultiplayerScreen mount effect fired `refreshLobbies()` while the socket was still connecting, so the `list_lobbies` request was silently dropped (list stayed empty until a manual refresh); (2) the server never pushed list changes, so a lobby created on another client never appeared. Fix: the server broadcasts `lobby_list` to every connected non-lobby client on lobby create/join/leave/removal (`broadcastLobbyList` in `server/index.ts`), and the store fetches the list on `welcome` (socket provably open) and again when a reconnect finds its old lobby gone. Covered by 2 new E2E tests (`src/net/multiplayer.e2e.test.ts`, "live lobby list"): a spectator sees a lobby appear live, its player count rise and fall as players join/leave, the host name transfer, private lobbies never leaking, and removal on last leave; plus the mount race — a fresh client whose refresh races the connect still gets the list without any manual refresh.
> - **Multiplayer game view UI** — ✅ REWORKED. The multiplayer screen now reuses the Versus (AI) layout: HOLD moved to the left column (it was on the right of the board), player stats + streak + match info + targeting in the left aside, player board with the incoming-lines meter flush right and NEXT beside it. The opponent view is now conditional on how many opponents remain: with exactly one (1v1), the full Versus-style panel appears — name, larger board (honors the `opponentBoardSize` setting: full 30px or small 16px), HOLD + NEXT pieces, SCORE/LINES/INCOMING stats, and the red incoming bar; with more than one opponent, a compact grid shows each board with the opponent's name above it, the red incoming bar, and the OUT/LEFT marker — no stats, no next pieces. To show the 1v1 opponent's hold and next pieces, the protocol now relays them: `snapshot` (client→server) and `board_update` (server→client) gained `hold`, `next`, and `lines` (optional with neutral defaults, so old clients still work). Covered by 2 new `MatchClient` unit tests (snapshot carries hold/next/lines; opponent state stores them from a relay) and extended E2E assertions proving B sees A's real hold ('I'), queue (matches A's engine), lines (2), and score through the real stack.
> - **Leavers not pruned from the game** — ✅ FIXED. Two issues: (1) `player_left` kept the leaver's board/hold/next/stats in the opponent's view, so a departed player stayed visible as a frozen "afk" board; `MatchClient` now prunes them (board/score/lines/incoming cleared, hold/next emptied) while keeping the `left` marker + wins, so the UI stops rendering the leaver entirely. (2) `Match.resolve` had a landmine: if the last remaining player was topped out (`alive=[]` with `players.size===1`), it hit the draw-replay branch and replayed games forever against an empty roster instead of ending the match — the "game continues with an afk player" behavior. It now resolves to `match_won` for the sole remaining player. Covered by a new engine test (lone dead player ends the match, no endless replay), a new MatchClient test (player_left prunes board/hold/next/stats), and extended E2E assertions in the 1v1 leave test (B's board/hold/next are empty after leaving, session reclaimed) and the 3-player leave test (leaver pruned from both survivors' views while the match continues).
> - **Switching targeting modes resets the board** — ✅ FIXED. The game screen's `useEffect` listed `targetMode` as a dependency, so switching targeting modes (button, or the server's auto-reassign echoed via `target_update`) tore down and rebuilt the `GameRunner`/`MatchClient` — a fresh `Game` with an empty board, losing all hold/combo/streak/piece-queue state (the board then "healed" via resync, masking the wipe). Fix: `targetMode` is read via a ref inside the loop (for the assist key) and removed from the effect deps, so switching modes only re-renders the HUD/buttons and never recreates the game. No DOM test harness exists in the repo (no jsdom/testing-library) so this is a wiring fix verified by typecheck/lint/build + the full suite rather than a mount test.
> - **Spectate / play toggle** — ✅ ADDED. Players can toggle between spectating and playing mid-match (`spectate` client message). The server marks spectators in the `Session` (never targeted, moves/topouts refused), the engine's new `Match.spectate` marks them out of the current game WITHOUT resolving it (a spectator can never be the accidental last-man-standing winner), and at each game start spectators are re-marked; if nobody is left to play the match ends with no winner (`match_end` now broadcasts with a null winner → clients show "MATCH OVER"). In a 1v1, the remaining active player plays on alone and wins the match when the round resolves. A `player_spectating` broadcast tells everyone else who is watching. The game screen gained SPECTATE/PLAY buttons and a dedicated spectator view: one or two watched players get the full side-by-side treatment (board, hold, next, stats, incoming bar — reusing the 1v1 panel), more than two get a compact grid of name + board (up to 4 per row, wrapping to a second row), and the spectator's client stops sending locks/snapshots/topouts while watching. Covered by: engine tests (spectate sits out the current game without resolving; re-marking at game start), a `Session` test (spectators are never targeted, toggling back restores eligibility), `MatchClient` tests (setSpectating gates all gameplay sends; player_spectating marks opponents; null-winner match_end reads MATCH OVER), and 2 E2E tests through the real stack (3-player: B spectates → A's attack skips B and hits C, the match continues for A and C, B toggles back and plays; 1v1: B spectates → A plays on alone and wins the match when the round resolves, both stay in the lobby).

## 1. Multiplayer foundation

- [x] Real-time networked play: players on different machines can play tetris against each other in the same match; the game is no longer limited to local and AI opponents.
- [x] Low latency: fast-paced play must stay responsive. Local input must never wait on the network; attacks and garbage land with minimal delay under normal network conditions, and the client should surface connection quality (latency) so players can see it.
- [x] Desync handling: the server is **authoritative for every player's board** (reconstructed from the cells each `lock` carries). It cross-checks client snapshots against the authority board, acks a match, and sends a corrective `resync` on genuine divergence; a healthy snapshot is never rewritten. The client applies a legitimate `resync` to heal real desyncs. Anti-corruption guarantee: a lost/duplicated message (e.g. a dropped `garbage`) surfaces on the authority board and is healed via resync — it can never silently wipe or corrupt a player's board; verified with `server/message-loss.test.ts`, `server/authority.test.ts`, `server/multiclient.test.ts`.

## 2. Lobbies

- [x] Lobby creation from the main menu: a player creates a lobby and becomes its host.
- [x] Join code: every lobby is assigned a short join code made of letters and numbers at creation; the code is unique among active lobbies and shown to the host and players so others can join with it.
- [x] Join by code: any player can enter a join code to join that lobby.
- [x] Public vs private: the creator chooses at creation whether the lobby is public (listed on a public registry) or private (joinable only by code).
- [x] Public registry: a "lobbies" tab in the main menu lists public lobbies — host name, player count, and a summary of room settings — and allows joining directly from the list.
- [x] The lobby disapears and gets cleaned up nicely after all players leave.

## 3. Lobby view

- [x] Players land in a lobby view after creating or joining a lobby, before any match starts.
- [x] Roster: the lobby view shows who is in the lobby, with the host clearly marked.
- [x] Room settings: the lobby view shows the room settings (scoring options, etc.) to everyone in the lobby.
- [x] Host-only editing: only the host can change room settings; changes apply live and are visible to all players in the lobby.
- [x] Leaving: players can leave the lobby at any time; if the host leaves, the lobby is transferred to the next oldest member without stranding the remaining players.

## 4. Match lifecycle

- [ ] Host start: when the host clicks start, all players in the lobby transition together into an active session (match).
- [ ] Rounds: a match is a series of games; each game is last-man-standing — players who top out are eliminated and the game continues until one survivor remains; the result is shown, and the next game starts automatically until the match win condition is met.
- [ ] Match end: when the match's win condition is met, the session ends, results are shown to all players, and players return to the lobby view.
- [x] Disconnects: a player disconnecting mid-match must not crash or hang the session; remaining players are notified, a mid-game disconnect forfeits that game, and the match resolves according to the disconnect policy. _(Fixed + tested under the adversarial pass: leavers are permanently removed (`Match.removePlayer`) instead of being forfeited-per-round, so a sole surviving opponent isn't left with a ghost that never tops out; adds `src/engine/match.ts#removePlayer`, engine unit tests, and `server/disconnect.test.ts` integration test.)_

## 5. Competitive scoring options

- [ ] Matches are decided by games won, not by lines sent: the match win condition is evaluated across a series of games, never inside a single board.
- [ ] Last-man-standing: a player who tops out is eliminated for that game and play continues; the game ends when only one player remains, and that survivor wins the game.
- [ ] First to X: the match ends as soon as a player has won X games (X is host-configurable; e.g., first to 5, first to 7, first to X).
- [ ] Win by X: the match only ends when a player leads by at least X games won (e.g., win by 2), so a one-game lead cannot close the match; ties and smaller leads keep the match going.
- [ ] Room settings: scoring mode and its values are room settings adjustable by the host before the match starts.
- [ ] Between games: a brief results screen shows who won the game and the running match score, then the next game starts automatically.
- [ ] Progress display: each player's wins and the match goal are visible in the HUD during play (e.g., 3/7).
- [ ] Simultaneous top-out: if the final players top out at the same time there is no survivor, and the game resolves per policy (recommended: no win awarded, game replayed).

## 6. Multiplayer competitive view

- [ ] 1v1 layout: with a single opponent, the existing side-by-side view is preserved (player's board on the left, opponent board with mirror info on the right).
- [ ] N-player layout: with more than one opponent, the player's board stays on the left and all opponent boards are shown to the right of the player's board.
- [ ] Per-opponent info: each opponent view shows their board plus per-player info (name, wins, incoming garbage, streak).
- [ ] Scaling: opponent boards scale so any number of opponents (up to the lobby cap) fits on screen.
- [ ] Elimination display: topped-out players are marked as eliminated (e.g., dead board) for the rest of the game, and they can no longer be targeted.

## 7. Garbage targeting

- [ ] Targeting modes: when sending garbage, the player chooses where it goes via three modes — manual, revenge, random — switched with the number keys (defaults 1/2/3).
- [ ] Manual: the player clicks an opponent's board to select them as the target; attacks go to that opponent until changed.
- [ ] Revenge: attacks go to the opponent who most recently attacked the player.
- [ ] Random: attacks go to a randomly chosen opponent.
- [ ] Target icon: in all modes, a target icon is shown over the board of the player currently being targeted.
- [ ] Fallbacks: if the current target is eliminated or disconnected, manual auto-reassigns to a random living opponent (mode unchanged) and revenge falls back to the most recent living attacker, then to random; when only one opponent remains, all modes route to them.
- [ ] Targeting applies to all garbage sent by clears (attacks, combos, streaks); with a single opponent the modes still exist but routing is trivially moot.
- [ ] Targeting state (mode, manual target, attacker history) resets at the start of each game.

## 8. Engineering & testing

- [ ] Server component: a small server hosts lobbies, the public registry, and match relay; it is the authority on room settings, scoring, targeting, and desync resolution.
- [ ] Shared protocol: a single source of truth for the message types shared between client and server, so the two sides cannot drift apart.
- [ ] Tests: match win conditions (first-to-X, win-by-X) and round flow, targeting routing, lobby lifecycle, and desync detection/resync are unit-tested; at least one simulated message-loss test proves attacks/garbage stay consistent when messages are dropped.
- [ ] Docs updated: `notes/tech-stack.md` and `AGENTS.md` are updated as the stack and project rules change (the project is no longer "no backend").

## Reconnect resilience (added pass)

- [x] **Unexpected disconnect = grace buffer, not instant prune** — a socket close without a prior leave now keeps the player in the lobby + match for a grace period (default 20s, `setReconnectGraceMs` exported for tests): the roster marks them `reconnecting`, they are sat out of the current game (engine `spectate` — a ghost can't win) and excluded from targeting (session spectator) while gone. When the grace expires (`pruneBuffered`) they are forfeited and removed exactly as before. An intentional leave (`leave_lobby`, `dismiss_rejoin`, or the app's disconnect while in a lobby) is still pruned instantly.
- [x] **Rejoin by id** — `hello` now carries the persisted `selfId` (`rejoinId`); a matching buffered player has their identity adopted and receives `rejoin_offer` (sent before `welcome` so the client can act in order). `rejoin` attaches the connection to the lobby + match (lobby_state + a re-keyed `match_start` carrying the current `round`), un-spectates and `revive`s them into the running round (genuine lobby spectators stay spectating); `dismiss_rejoin` prunes instantly.
- [x] **Client flows** — `selfId` persisted across refreshes; in-app reconnect (network blip) auto-accepts the offer silently (the user never left); a fresh page load surfaces `pendingRejoin` and MultiplayerScreen shows a REJOIN GAME? popup (REJOIN / DISMISS). `match_start.round` seeds the MatchClient so a rejoined player drops into the right round (board relays aren't lost).
- [x] **MatchClient** — constructor takes the current round from match_start; a rejoined client resyncs to the authoritative board (which was frozen, not lost, while they were away).
- Tests: engine `revive` unit tests; reworked server tests (disconnect keeps the opponent buffered then awards the match after grace; lifecycle forfeits after grace; integration host-transfer happens after grace); load tests use a short grace so closed sockets prune quickly; E2E: in-app drop → auto-rejoin back into the match with no match_end for the opponent, refreshed client → offer → popup → REJOIN returns to the live match, DISMISS prunes instantly, both-disconnect leaves zero state after grace, disconnect-at-match_end reclaims after grace. All end-of-test exits go through `closeClient` (intentional leave) so buffered ghosts never leak between tests.

## Score fix (round intermission + game score award)

- [x] **Intermission shows after every round** — root cause: `MultiplayerGameScreen`'s match effect listed `onExit` in its deps, and `onExit` is a fresh closure on every App render; any `roster_update` during the match (joins/leaves/spectate, and previously the per-round +1 broadcast) re-rendered App, which tore down and rebuilt the MatchClient mid-match — wiping the intermission state a frame after `game_end` set it, so the scoreboard only ever survived on `match_end` (which re-sets it on the fresh client). Fix: `onExit` is read via a ref and removed from the effect deps (same pattern as the earlier `targetMode` fix). Proven by a new E2E test: a round ending mid-match opens the intermission on both clients with the round's scores, and the match continues to round 2.
- [x] **Game score = +1 for the match winner only** — the award moved from `game_won` (per round) to `match_won`: the series winner gets exactly +1 on their lobby member, others get nothing, and no roster broadcast fires per round anymore (which also removes the App-re-render trigger at round end). E2E: mid-match the roster stays 0/0; after a 3-0 match the winner is at 1 and the loser at 0.
