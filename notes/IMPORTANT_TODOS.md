- [x] Game loss doesnt work at all. When one player dies their board state gets stuck on the opponent's client. On their client, they keep seeing the scoreboard pop up over and over again but the round doesnt progress. When a player dies scoreboard is stuck with 0 points for both players. — FIXED. Two interrelated bugs: (1) a top-out finalized the shared `GameRunner` (singleplayer end-of-run semantics set `ended` permanently), so after the next round's `game_start` restored a fresh board the runner refused to tick — the dead player became a frozen zombie and the round could never resolve. `GameRunner.reset()` now un-finalizes it on a round change (`MultiplayerGameScreen`). (2) The intermission dismissal was one-sided: the UI cleared its local copy after ~4s but `MatchClient.state.intermission` stayed set, so any later relay (e.g. the opponent's ~10Hz board_update) resurrected the scoreboard. `client.clearIntermission()` now keeps the store in sync. Covered by a `GameRunner` unit test and a `MatchClient` test. FURTHER fixes from faithful GameRunner-driven E2E (`src/net/round-transition.e2e.test.ts`, which drives the same `GameRunner`+`MatchClient` the game screen uses instead of raw `game.tick()`): (a) a round-ending topout broadcast `game_end` TWICE (once for `eliminated`, once for `game_won`) — made the server look like the player was dying over and over; the standalone `eliminated` broadcast is now suppressed when the batch also resolves the round, so each death resolves exactly once. (b) `game_start` reused the previous round's hidden top rows, and a topped-out board has blocks piled in them — so the revived player's piece spawned into residual blocks and instantly re-topped-out every round ("board not cleared", "scoreboard stuck at 0" because rounds ended before anyone could score). `game_start` now builds clean (four-wide-walled) hidden rows. (c) `MatchClient.lastSnapshot`/`snapshotSeq` weren't reset on `game_start`, throttling the revived player's first relay against the prior round's frame count — now reset so their fresh board reaches the opponent immediately. Updated `server/lifecycle.test.ts` to the corrected single-`game_end` semantics; suite 264 green.
- [x] When you refresh or rejoin the page, there is no popup to rejoin your last lobby. — FIXED. Root cause: when a page refresh's new socket reached the server BEFORE the old socket's `close`, the player wasn't in the rejoin `buffered` map yet, so `hello` treated them as brand-new and never sent `rejoin_offer`. `server/index.ts` now also offers a rejoin when the presented `selfId` is a currently-live member (close still in flight), materializing the buffer on the spot so the popup (+ REJOIN/DISMISS + grace) all work. E2E proven: a reconnect that beats its own close still surfaces the popup.
- [x] When a player manually rejoins a lobby after going into the reconnecting state, there are two copies of that player, where one is reconnecting and the other is the new player state. — FIXED. Same root cause as above: the refresh racing its own close fell through to a brand-new id (and the delayed old close buffered the `reconnecting` copy), so a fallback `join_lobby` added a second member. With `hello` now claiming the rejoinId of a live member, the identity is preserved (no fresh id, no re-join as a new player), and the delayed old socket's close is treated as superseded (`conns.get(conn.id) !== conn`) so it can neither re-buffer nor re-mark `reconnecting`, nor yank the live claimer's routing. E2E proven: exactly one member, reconnect flag cleared, no duplicate before or after the delayed close.
