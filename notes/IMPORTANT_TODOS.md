- [x] Game loss doesnt work at all. When one player dies their board state gets stuck on the opponent's client. On their client, they keep seeing the scoreboard pop up over and over again but the round doesnt progress. When a player dies scoreboard is stuck with 0 points for both players. — FIXED. Two interrelated bugs: (1) a top-out finalized the shared `GameRunner` (singleplayer end-of-run semantics set `ended` permanently), so after the next round's `game_start` restored a fresh board the runner refused to tick — the dead player became a frozen zombie and the round could never resolve. `GameRunner.reset()` now un-finalizes it on a round change (`MultiplayerGameScreen`). (2) The intermission dismissal was one-sided: the UI cleared its local copy after ~4s but `MatchClient.state.intermission` stayed set, so any later relay (e.g. the opponent's ~10Hz board_update) resurrected the scoreboard. `client.clearIntermission()` now keeps the store in sync. Covered by a `GameRunner` unit test and a `MatchClient` test. FURTHER fixes from faithful GameRunner-driven E2E (`src/net/round-transition.e2e.test.ts`, which drives the same `GameRunner`+`MatchClient` the game screen uses instead of raw `game.tick()`): (a) a round-ending topout broadcast `game_end` TWICE (once for `eliminated`, once for `game_won`) — made the server look like the player was dying over and over; the standalone `eliminated` broadcast is now suppressed when the batch also resolves the round, so each death resolves exactly once. (b) `game_start` reused the previous round's hidden top rows, and a topped-out board has blocks piled in them — so the revived player's piece spawned into residual blocks and instantly re-topped-out every round ("board not cleared", "scoreboard stuck at 0" because rounds ended before anyone could score). `game_start` now builds clean (four-wide-walled) hidden rows. (c) `MatchClient.lastSnapshot`/`snapshotSeq` weren't reset on `game_start`, throttling the revived player's first relay against the prior round's frame count — now reset so their fresh board reaches the opponent immediately. Updated `server/lifecycle.test.ts` to the corrected single-`game_end` semantics; suite 264 green. SCOREBOARD SIMPLIFIED: the intermission now shows ONLY the round outcome — the round's winner gets +1, everyone else 0 (all 0 on a draw). All accumulated-score machinery was ditched: `Session` no longer tracks per-player scores at all (no attack-line totals, no mirrored engine points), `LockEvent.score` and `resync.score` are gone, and the server builds the `scores` map straight from the match result (`roundScores` in `server/index.ts`). The in-game HUD score and the opponent panel's live score remain engine points — only the between-round scoreboard is the 1/0 round score. E2E asserts winner 1 / loser 0 on the scoreboard. - [x] When you refresh or rejoin the page, there is no popup to rejoin your last lobby. — FIXED. Root cause: when a page refresh's new socket reached the server BEFORE the old socket's `close`, the player wasn't in the rejoin `buffered` map yet, so `hello` treated them as brand-new and never sent `rejoin_offer`. `server/index.ts` now also offers a rejoin when the presented `selfId` is a currently-live member (close still in flight), materializing the buffer on the spot so the popup (+ REJOIN/DISMISS + grace) all work. E2E proven: a reconnect that beats its own close still surfaces the popup.
- [x] When a player manually rejoins a lobby after going into the reconnecting state, there are two copies of that player, where one is reconnecting and the other is the new player state. — FIXED. Same root cause as above: the refresh racing its own close fell through to a brand-new id (and the delayed old close buffered the `reconnecting` copy), so a fallback `join_lobby` added a second member. With `hello` now claiming the rejoinId of a live member, the identity is preserved (no fresh id, no re-join as a new player), and the delayed old socket's close is treated as superseded (`conns.get(conn.id) !== conn`) so it can neither re-buffer nor re-mark `reconnecting`, nor yank the live claimer's routing. E2E proven: exactly one member, reconnect flag cleared, no duplicate before or after the delayed close.
- [x] Member ends up playing on the SAME board as the host after leaving + refreshing + rejoining. — FIXED. Two layers caused it. (1) CLIENT: the persisted identity (`selfId`) lived in `localStorage`, which every tab/window of one browser SHARES — so the member's refresh could present the HOST's id. `src/state/identity.ts` now keeps `selfId` in `sessionStorage` (per-tab: survives a refresh, invisible to sibling tabs) and only the display name in `localStorage`; the store no longer uses zustand persist for identity. Unit-tested: two tabs keep distinct ids, each refresh keeps its own tab's id. (2) SERVER: the earlier "live-member" rejoin claim granted ANY socket presenting a live member's id that identity ON SIGHT — a refresh racing its own close legitimately needs this, but a different client presenting a shared/collided id got the host's identity too: shared authority, shared board, placements landing on the host's side. `server/index.ts` now holds such claims in a `pendingClaims` window (default 3s, `setClaimWindowMs` for tests): when the member's own socket closes the claim completes (real refresh), and when the window expires the presenter starts fresh — a live member's identity is never granted to a socket whose predecessor never closed. Refactored the claim body into `adoptRejoin`. E2E: a member whose refresh presents the HOST's id gets a brand-new id, no offer, no match, no resync on the host, and A still sees B's own board (proven to fail on the pre-fix server with `b2.selfId === aId`). The refresh-beats-its-own-close test now closes the old socket before the popup appears (the claim completes on the close). Suite 269 green.
